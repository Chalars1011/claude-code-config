# Systematic Debugging（系统化调试）

> 触发：任何 bug/测试失败/异常行为/构建失败。核心铁律：**不找到根因不许修**。

## 四阶段（必须按顺序）

### Phase 1: 根因调查（修之前必做）
1. 仔细读错误信息/堆栈（行号、错误码）
2. **建紧反馈环**：一条命令能复现症状（失败的测试/curl/CLI 脚本），跑得快、确定性强
3. 查最近改动：`git log --oneline -10`、`git diff`
4. 多组件系统：每层加诊断日志，先定位断在哪层
5. 追踪数据流：坏值从哪来？往上游追到源头

### Phase 2: 模式分析
- 找代码库里相似的可用实现，完整读，对比差异
- 列出所有不同点，别假设"这不重要"

### Phase 3: 假设与验证
- 先列 3-5 个可证伪假设，按"最可能+最便宜验证"排序
- 一次只改一个变量，最小探针验证
- 不灵 → 换假设，别叠补丁

### Phase 4: 实现修复
- 先写复现测试（RED），修根因（GREEN）
- 一次只修一处，不夹带重构
- **三连败 → 停**：质疑架构，别修第四个（说明架构错了不是假设错了）

## 红灯（出现即回到 Phase 1）
- "先快速修一下，回头再查" / "大概就是 X，试一下" / "一次改多处一起跑"
- 未追踪数据流就提方案 / 已试 2+ 次还要再来一次

## 快速参考
| 阶段 | 关键动作 | 成功标准 |
|---|---|---|
| 1 根因 | 读错误、复现、查改动、追踪 | 理解 WHAT 和 WHY |
| 2 模式 | 找可用参照、对比差异 | 知道差在哪 |
| 3 假设 | 排序假设、最小验证 | 确认或换假设 |
| 4 修复 | 先测试后修复、验证 | 修复且全测过 |

## 成果参考
系统化：15-30 分钟修好，95% 一次对。乱试：2-3 小时，40% 一次对。
