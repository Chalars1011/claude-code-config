# Spike（快速验证想法）

> 触发：不确定方案能不能行、技术路线有疑问、需要试错探索。"先证明能跑，再正式做。"

## 流程
1. **定义问题**：一句话：要验证什么？"能不能用 X 做到 Y"
2. **限定时间**：给自己一个死线（spike 不超过 1-2 小时）
3. **最小实验**：只写验证核心问题的最小代码
   - 能用现成库就绝不自己写
   - 不优化、不重构、不写测试（探索阶段）
4. **记录结论**：能行/不能行/部分可行 + 关键坑 + 参考代码
5. **处置**：
   - 能行 → 正式开工（重写正式版，别把 spike 代码直接当生产代码）
   - 不能行 → 记录原因，换方案

## 与正式开发的区别
| Spike | 正式代码 |
|---|---|
| 验证想法 | 交付功能 |
| 可脏可乱 | 要整洁可维护 |
| 不留测试 | 要有测试 |
| 有死线 | 按需求节奏 |

## 坑
- Spike 成功 ≠ 方案无风险（只证明"核心点"能跑）
- 别把 spike 代码留进生产（重写一遍比修 spike 快）
